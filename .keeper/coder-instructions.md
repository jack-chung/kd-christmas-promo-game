## Coder task scope
The planner specifies what to change and why, plus constraints that are not obvious from the code. The coder figures out how.

Write coder tasks at this level:
- What behavior or output needs to change
- What must not be touched and why
- Non-obvious constraints (schema compatibility, migration safety, commit ordering)

Do NOT include in coder tasks:
- Which specific functions or variables to edit
- Exact shell commands for standard operations
- Implementation approach when multiple valid approaches exist

## Deployment discipline
Never deploy to production unless the current task explicitly instructs a prod
deployment. If a task says "deploy" without specifying the environment, assume
dev/staging only. Completing a fix does not imply releasing it -- wait for
explicit per-session prod sign-off.

## Missing context recovery
Workflow files provide compact operational context, not a perfect transcript of every coder interaction.
If important implementation reasoning, architectural tradeoffs, proposal details, error output, or coder chat nuance is missing from the transition files, ask the user for a targeted copy/paste from the coder chat history.
Use narrow requests such as:
- "Please paste the coder's reasoning about the refactor."
- "Please paste the relevant error/output."
- "Please paste the implementation proposal discussion."
Treat pasted chat excerpts as temporary detail for the immediate problem. Do not preserve them in long-term workflow files unless they lead to a durable decision, plan change, or implementation constraint.

## Coder rules
Use project-owned ops scripts when they fit:
- If the project provides scripts for post-coding mechanics such as commit, merge/promote, build/package, or deploy/install, invoke the relevant script as one command instead of hand-rolling the sequence.
- Keep coder judgment inline: compose the commit message, choose what to stage, resolve conflicts, and perform live smoke/verification yourself.
- This applies only to scripts the project already provides; do not create ops scripts unless the task asks for them.

Treat project-owned tooling as improvable:
- A failing check usually indicates a real problem. First understand what the tool caught before deciding the tool is inadequate.
- For project-owned scripts or gates, distinguish a true failure from a mis-calibrated gate or uncovered scenario.
- When the tool is the problem, propose a concrete improvement in coder-report and implement it when low-risk so the workflow converges.
- Bypassing or skipping a check is a human sign-off decision. Surface the reason and never silently bypass a gate that exists to stop bad output.

## Resume rules
`.keeper/session-resume.md` is the PRIMARY handoff for same-repo fresh sessions, vendor switching, quota recovery, or session compaction. It is a cheap, curated pointer -- keep it short.
When a task is complete and changes are committed, update `.keeper/session-resume.md` to reflect the current state. Keep it under 30 lines -- include only: current version, current focus, next action, blockers. Move anything else to MASTER_PLAN.md or coder-report.md. Also record the freshness stamp and Source-session pointer described below.

When you WRITE/UPDATE the resume file, record at the bottom:
- `Last updated: <YYYY-MM-DD HH:MM> (session <vendor> <session-id>)` -- the freshness stamp.
- `Source session: <vendor> <session-id> -- <transcript path>` -- the chat this state came from. Claude transcripts: `~/.claude/projects/<project-slug>/<session-id>.jsonl` (the session id IS the transcript filename). Codex rollouts: `~/.codex/sessions/YYYY/MM/DD/rollout-*-<session-id>.jsonl`. If the session id is not readily available, record vendor + timestamp so the reader can still find the newest transcript.

When you RESUME from the resume file, before acting:
- If the file has NO freshness stamp, or its stamp is OLDER than the newest transcript for this project (a prior session likely ended at a cliff before updating it), treat the file as possibly stale and reconcile by scanning that newer transcript.
- To scan: read the Source-session transcript (or the newest one under the paths above) by grepping the TAIL, the last user turns, and decision points -- do NOT read a multi-MB transcript whole. Transcripts do not mark superseded plans, so on conflict the resume file / latest user intent wins.
- Precedence: ground truth from a scan overrides a STALE stamped summary; a FRESH stamped summary overrides a noisy scan.
Optional: when updating the resume file at session end, you may reconstruct it by scanning this session's transcript, so the next reader gets a distilled, current card.
